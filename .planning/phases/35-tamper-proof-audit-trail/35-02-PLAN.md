  <action>
Add a POST /audit/verify endpoint to the existing audit router. Admin-only (use get_current_active_admin dependency).

The endpoint logic:
1. Query all AuditLog records WHERE chain_sequence IS NOT NULL, ordered by chain_sequence ASC
2. Also count total records and records WHERE chain_hash IS NULL (pending — not yet processed by Celery)
3. Walk the chain:
   a. For each record, recompute content_hash using the same canonical JSON formula from the Celery task: `json.dumps({"id": str(id), "timestamp": isoformat, "entity_type": ..., "entity_id": ..., "action": ..., "user_id": ..., "before_state": ..., "after_state": ..., "details": ...}, sort_keys=True, default=str)`
   b. Compare recomputed content_hash with stored content_hash — if mismatch, record a "content_tampered" break
   c. Compute expected chain_hash from content_hash + previous chain_hash (or "GENESIS" for first record)
   d. Compare expected chain_hash with stored chain_hash — if mismatch, record a "chain_broken" break
   e. Check chain_sequence is consecutive (no gaps) — if gap detected, record a "sequence_gap" break
4. Return a response object:
   ```python
   {
     "status": "pass" | "fail",
     "total_records": int,
     "chained_records": int,
     "pending_records": int,  # chain_hash is NULL
     "breaks": [
       {
         "chain_sequence": int,
         "record_id": str,
         "type": "content_tampered" | "chain_broken" | "sequence_gap",
         "details": str
       }
     ],
     "verified_at": datetime
   }
   ```
5. Use `import hashlib, json` — same logic as the Celery task for hash computation.
6. Add a Pydantic response model `AuditVerifyResponse` and `AuditBreak` in the router file (or in schemas/audit.py — Claude's discretion, but keeping in schemas/audit.py is cleaner).

Use streaming query (yield_per or similar) if concerned about memory, but for typical audit logs (<100K records), a simple .all() is fine. Add a `limit` query param defaulting to 100000 to cap verification scope.
