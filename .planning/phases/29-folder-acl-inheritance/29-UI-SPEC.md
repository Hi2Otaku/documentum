## Component Inventory

### New Components (3)

#### 1. FolderPermissionsTab
**Location:** `frontend/src/components/folders/FolderPermissionsTab.tsx`
**Purpose:** Permissions tab content for the folder detail panel on FoldersPage.

- **Layout:** Vertical stack inside a `TabsContent` panel.
- **Header row:** `h4` "Permissions" (text-sm font-medium) with "Add Permission" `Button` (size="sm", primary variant) right-aligned. Uses `Shield` icon (16x16) from Lucide next to heading.
- **ACL list:** Vertical stack of ACL entry rows, each row is a horizontal flex container with:
  - Principal icon: `User` (16x16) for user principals, `Users` (16x16) for group principals, color `text-muted-foreground`.
  - Principal name: `text-sm` truncated with title tooltip.
  - Principal type label: `Badge` variant="outline", text "User" or "Group", `text-xs`.
  - Permission level: `Badge` variant="secondary", text is capitalized permission level ("Read", "Write", "Delete", "Admin"), `text-xs`.
  - Remove button: `Button` variant="ghost" size="icon" (h-7 w-7), `X` icon (14x14), `text-muted-foreground hover:text-destructive`.
- **Row spacing:** `gap-2` between rows, each row has `py-2 px-2 rounded-md hover:bg-muted` for hover feedback.
- **Empty state:** When no ACL entries exist, show: `Shield` icon (32x32, `text-muted-foreground`), heading "No permissions set", body "This folder is open to all users. Add a permission entry to restrict access." All centered vertically in the tab area.
- **Loading state:** 3x `Skeleton` rows (h-8 w-full) with `gap-2`.

#### 2. AddPermissionDialog
**Location:** `frontend/src/components/folders/AddPermissionDialog.tsx`
**Purpose:** Dialog for adding a folder ACL entry (select principal + permission level).

- **Trigger:** "Add Permission" button in FolderPermissionsTab header.
- **Component:** `Dialog` (shadcn) with `DialogHeader`, `DialogContent`, `DialogFooter`.
- **Title:** "Add Permission" (text-lg font-semibold).
- **Description:** "Grant a user or group access to this folder and its documents."
- **Form fields (vertical stack, gap-4):**
  1. **Principal type toggle:** Two-segment inline radio using two `Button` variant="outline" side by side. Left: "User" with `User` icon. Right: "Group" with `Users` icon. Active segment gets `variant="default"` (primary fill). Fixed height h-9.
  2. **Principal selector:** `Select` (shadcn) dropdown. Placeholder: "Select a user..." or "Select a group..." depending on toggle. Options populated from `/api/v1/users` or a groups endpoint. Each option shows username/group name. Full width.
  3. **Permission level:** `Select` (shadcn) dropdown. Options: "Read", "Write", "Delete", "Admin". Default selection: "Read". Full width.
- **Footer:** "Cancel" (`Button` variant="outline") and "Add Permission" (`Button` variant="default", primary). "Add Permission" disabled until both principal and permission are selected.
- **Error state:** Inline `text-sm text-destructive` below form fields. Copy: "Failed to add permission. The user may already have an entry on this folder."
- **Dialog width:** `sm:max-w-[425px]` (shadcn default dialog).

#### 3. AccessSourceBadge
**Location:** `frontend/src/components/documents/AccessSourceBadge.tsx`
**Purpose:** Shows "Inherited from folder: [name]" badge on DocumentDetailPanel when access derives from folder ACL.

- **Visibility:** Only rendered when the API response includes `access_source === "folder_inherited"` and `access_source_folder_name` is present.
- **Component:** `Badge` variant="outline" with a `FolderOpen` icon (12x12) inline before text.
- **Copy:** "Inherited from [folder_name]" where folder_name is the resolved folder name.
- **Placement:** In DocumentDetailPanel, below the lifecycle/lock badges row (after line ~128 in existing code), as an additional flex item in the badge row.
- **Styling:** `text-xs`, `border-blue-200 text-blue-700 bg-blue-50` (uses Tailwind direct colors since there is no semantic "info" token in the current theme). This distinguishes it visually from the neutral outline badges.
- **Not shown:** When `access_source === "direct"` or `access_source === "open"`.

## Interaction Contract

### Add Permission Flow
1. User selects a folder in the tree.
2. User clicks "Permissions" tab.
3. User clicks "Add Permission" button.
4. Dialog opens. User toggles "User" or "Group", selects a principal from dropdown, selects permission level.
5. User clicks "Add Permission" in dialog footer.
6. On success: dialog closes, ACL list refreshes via `queryClient.invalidateQueries`. Toast/inline feedback not required (list update is immediate visual confirmation).
7. On error: inline error message appears below form fields in dialog. Dialog stays open.

### Remove Permission Flow
1. User clicks `X` button on an ACL entry row.
2. `window.confirm` prompt: "Remove [permission] access for [principal_name]?"
3. On confirm: mutation fires, row disappears from list on success.
4. On error: existing error handling pattern (thrown error caught by mutation).

### Access Source Badge Display
1. DocumentDetailPanel fetches document detail.
2. API response includes `access_source` field ("direct" | "folder_inherited" | "open") and optional `access_source_folder_name`.
3. If `access_source === "folder_inherited"`: render `AccessSourceBadge` in the badges row.
4. If `access_source === "direct"` or `"open"`: badge not rendered.

### Data Fetching

| Query Key | Endpoint | Trigger |
|-----------|----------|---------|
| `["folders", folderId, "acl"]` | `GET /api/v1/folders/{id}/acl` | Permissions tab mounts |
| (mutation) | `POST /api/v1/folders/{id}/acl` | Add Permission dialog submit |
| (mutation) | `DELETE /api/v1/folders/{id}/acl/{acl_id}` | Remove button click + confirm |
| `["users"]` or `["groups"]` | `GET /api/v1/users` / groups endpoint | AddPermissionDialog principal dropdown opens |
